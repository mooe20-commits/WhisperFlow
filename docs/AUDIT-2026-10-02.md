## Architecture Overview

Menu-bar-only app (`accessory` policy). Data flow:

```
CGEvent tap (HotkeyManager, runloop-source thread + 50ms NSEvent poll fallback)
  → PTT down/up | double-tap → continuous (Esc/Bksp/Del cancels, any key/click commits)
  → TranscriptionController (captureQueue serial: AVAudioEngine → tap → AVAudioConverter → WAV in ~/Library/Caches)
  → hotkey UP → transcribe: daemon (Unix-socket line-JSON, 8s recv cap) → fallback subprocess wf-transcribe (15s watchdog, concurrent stderr drain)
  → filler + grammar → TextInjector on main: AX in-place (partials/natives) | pasteboard+Cmd+V (final, clipboard-ON) | CGEvent keystrokes (final, Electron/clipboard-OFF)
  → icon flips idle→ptt/transcribing→idle (generation-guarded, 300ms min-visible)
```

Thread boundaries: tap thread, captureQueue, global(qos) transcribe/partial workers, main (timers, inject, icon). Shared state: `isCapturing`, `partialInFlight`, `wavByteOffset`, `lastPartialText`, `iconGeneration`, daemon recv buffer (lock-confined — good).

## Findings

### 🔴 B1 — `stopDaemon` blocks main up to 3s

**Location:** `Sources/WhisperFlow/AppDelegate.swift:688-697`
**Symptom:** Switching engine to subprocess (menu click → `selectEngine` → `stopDaemon` on main) or quitting with daemon engine freezes the menu-bar UI for up to 3s in the `while Date() < deadline { Thread.sleep(0.1) }` poll loop.
**Fix:** move the wait loop to a background queue; flip the icon/menu state optimistically:
```swift
DispatchQueue.global(qos: .utility).async {
    let deadline = Date().addingTimeInterval(3.0)
    while Date() < deadline {
        if !TranscriptionDaemon.isRunning() { wfLog("[WF:App] stopDaemon: daemon exited"); return }
        Thread.sleep(forTimeInterval: 0.1)
    }
    wfLog("[WF:App] stopDaemon: WARNING — daemon still running after 3s")
}
```
**Why it matters:** user-visible hang on a routine menu action — the exact class v0.9.7 FIX-R2 already eliminated for capture setup.
**Last verified:** FIX (not shipped). `stopDaemon` + 3s poll added in v0.9.8 (daemon-by-default); no session moved the wait off main. CHANGELOG 0.9.8 confirms the feature, not the threading.

### 🔴 B2 — Stale PID file silently disables the daemon forever

**Location:** `Sources/WhisperFlow/TranscriptionDaemon.swift:31-38` + `Sources/WhisperFlow/AppDelegate.swift:739`
**Symptom:** `isRunning()` is `kill(pid,0)==0` with no identity check. If the PID file is stale and the PID got recycled, `ensureDaemonRunning` concludes "already running, skipping launch" — the daemon is never launched, and *every* dictation pays subprocess latency plus a "daemon not reachable" warning. Self-healing never triggers because the check that would relaunch is the one being fooled.
**Fix:** verify identity inside `isRunning()` using the existing `ProcInfoHelper` (currently only used on the stop path):
```swift
static func isRunning() -> Bool {
    guard let pidStr = try? String(contentsOfFile: pidPath, encoding: .utf8),
          let pid = pid_t(pidStr.trimmingCharacters(in: .whitespacesAndNewlines)),
          kill(pid, 0) == 0 else { return false }
    guard let path = ProcInfoHelper.pathOfPID(pid) else { return false }
    return path.hasSuffix("wf-transcribe-daemon") || path.contains("python")
}
```
**Why it matters:** single-point failure for the default engine path; failure mode is silent slowness, hard to diagnose.
**Last verified:** FIX (gap around shipped fix). FIX-R7 (v0.9.7, CHANGELOG 0.9.7) added `proc_pidpath` verification to the `stopDaemon` SIGTERM path only — `isRunning()` and `ensureDaemonRunning` were never covered. `git log --oneline` shows no later touch to `TranscriptionDaemon.isRunning`.

### 🔴 B3 — Re-tapping hotkey in continuous mode clobbers mode to `.ptt`

**Location:** `Sources/WhisperFlow/HotkeyManager.swift:279-291` → `429-459`
**Symptom:** In continuous mode, pressing the combo again routes to `handleHotkeyDown`, which — outside the 1.0s double-tap window — sets `mode = .ptt` and fires `onHotkeyDown` → `startCapture()` (ignored by guard, but the mode is now wrong). Consequences: the continuous cap timer leaks (never invalidated on the PTT path), and the next keyUp commits via the PTT branch instead of the continuous branch. Repro: double-tap into continuous, wait 2s, tap combo once, release — recording commits as PTT, cap timer still armed.
**Fix:** early-out at the top of the keyDown branch:
```swift
if type == .keyDown {
    if mode == .continuous, isOurCombo {
        isHeld = true
        return nil  // swallow; combo does not exit or restart continuous
    }
    ...
}
```
**Why it matters:** corrupts the recording state machine; leaked 5-min timer can later fire `exitContinuous` against an unrelated session.
**Last verified:** FIX (not shipped). Continuous mode added v0.7.3; no handoff/CHANGELOG entry covers combo-press-during-continuous. `git log` shows no HotkeyManager change since the double-tap routing fix.

### 🔴 B4 — `deleteLastPartial` lacks the 200-char back-extend cap

**Location:** `Sources/WhisperFlow/TextInjector.swift:444-456` (compare caps at `:130` and `:355`)
**Symptom:** `partialReplace` (FIX-10) and `injectViaAX` both cap the back-extend at 200 chars, but `deleteLastPartial` uses raw `prev.count`. A stale/long `lastPartialText` (exactly the scenario FIX-8 was defending against) makes the commit path select and delete up to `prev.count` chars of the user's real text before pasting the final. The two sibling call sites were hardened; this one was missed.
**Fix:** mirror the sibling pattern:
```swift
let backExtend = min(prev.count, 200)
let newLocation = max(0, cursor - backExtend)
let newLength = min(cursor, backExtend)
```
**Why it matters:** data loss (deletes user text) on the commit path — the highest-traffic path in the app.
**Last verified:** FIX (gap around shipped fix). FIX-10 cap shipped (visible at `:130`,`:355`); `git show 748e05a` + `49a6f2e` touched `inject()`/Electron routing only, never `deleteLastPartial`. CHANGELOG has no entry for it.

### 🟡 R1 — Daemon send has no timeout; recv does

**Location:** `Sources/WhisperFlow/TranscriptionDaemon.swift:163-173` (vs 8s recv cap at `:205-229`)
**Symptom:** `sendSem.wait()` blocks indefinitely. If the connection drops between ready and send-completion, the worker thread hangs forever (not main, but leaks a thread + the transcription never completes → icon stuck until another path fires). Sequence is rare but the asymmetry is deliberate-looking and wrong.
**Fix:** `if sendSem.wait(timeout: .now() + 2.0) == .timedOut { connection.cancel(); throw DaemonError.connectionFailed("send timeout") }`.
**Last verified:** FIX. FIX-13 (v0.9.7) capped recv at 8s; send was never capped. No later commit touches `sendBlocking`.

### 🟡 R2 — Tap + poller both fire `onHotkeyUp`

**Location:** `Sources/WhisperFlow/HotkeyManager.swift:310-334` vs `:412-422`
**Symptom:** On every PTT release the tap fires `onHotkeyUp` *and* the 50ms poller fires it again. Today `stopCapture`'s `isCapturing` guard absorbs the duplicate (log noise only), but two `stopCapture` dispatches per press means two `finishStopCapture` queue hops — if the guard ever relaxes, double transcription/injection. The code comments acknowledge the overlap without resolving ownership.
**Fix:** single owner — let the tap own keyUp; poller only fires `onHotkeyUp` if the tap has been silent for >200ms (or add the `iconGeneration`-style generation counter used for icon flips).
**Last verified:** FIX. Known overlap, never owned. VERIFY-adjacent: the `isCapturing` guard (FIX-R2, v0.9.7) is what makes this benign today — do not remove that guard.

### 🟡 R3 — Partial byte offset assumes 16-bit PCM on disk

**Location:** `Sources/WhisperFlow/TranscriptionController.swift:171,603`
**Symptom:** `wavByteOffset += frames * 2` assumes 2 bytes/frame, but the `AVAudioFile` is opened with `commonFormat: .pcmFormatFloat32` (`:727-732`) while settings say 16-bit — actual bytes-per-frame on disk depends on which wins. If Float32 wins, every partial slice sent to the daemon (`sendPartialTranscription` `:639-659`) under-counts by 2× and the daemon transcribes the wrong window (stale/truncated partials).
**Fix:** derive bytes-per-frame from `writer.file.processingFormat` (or `streamDescription.mBytesPerFrame`) instead of hard-coding 2; assert `wavByteOffset` against actual file size in debug.
**Last verified:** FIX. Never verified in any session; partials default OFF (FIX-12) so blast radius is currently small — verify before re-enabling by default.

### 🟡 R4 — Stereo input silently drops channel 1

**Location:** `Sources/WhisperFlow/TranscriptionController.swift:561` (`floatChannelData?[0]`)
**Symptom:** USB mics presenting stereo feed only channel 0 to the converter and energy tracker. No warning even though `inputFormat.channelCount` is logged at setup. Typically benign (dual-mono), but a right-only source records silence.
**Fix:** average channels explicitly, or `wfLog` when `channelCount > 1` so the diagnostic exists.
**Last verified:** FIX. Listed in the audit-patterns reference as a known class; never addressed in this repo's history.

### 🟡 R5 — First partial waits a full cadence

**Location:** `Sources/WhisperFlow/TranscriptionController.swift:305-314`
**Symptom:** Timer starts at capture; first partial fires after 1.0s (balanced). Utterances <1s never show a preview. Low stakes today (partials default OFF).
**Fix:** schedule first fire at `min(cadence, 0.3)`, subsequent at cadence (one-shot → repeating handoff).
**Last verified:** FIX. Pattern-reference recipe exists; never applied here.

### ⚡ O1 — Electron check hits disk on every final inject, and misses non-Electron Chromium

**Location:** `Sources/WhisperFlow/TextInjector.swift:49-57,75-86`
**Symptom:** Every pasteboard-free final runs `contentsOfDirectory` on the frontmost app's `Frameworks/` dir synchronously (TC calls `inject` on main, `:1038`). Two issues: (a) disk I/O on the keystroke-latency path; (b) Chrome/Chromium (non-Electron) don't bundle an `*Electron*` framework — per the `49a6f2e` premise ("newer Chromium drops AX writes"), those apps fall through to the AX path whose write "succeeds" but lands nowhere → silent transcript loss, the exact bug just fixed for Electron.
**Fix:** cache the verdict per frontmost bundle-ID with a short TTL; broaden detection (bundle-ID prefixes `com.google.Chrome`, `org.chromium`, `com.microsoft.edgemac`, or `Chromium`/`CrRenderer` framework names); consider keystroke-first for all Chromium once verified.
**Last verified:** FIX (follow-up to shipped). `49a6f2e` + `748e05a` (2026-10-02) shipped the Electron bypass — VERIFY they work for Electron; the caching + non-Electron-Chromium gap is new.

### ⚡ O3 — `usleep(20ms)` on main in both inject paths

**Location:** `Sources/WhisperFlow/TextInjector.swift:198,300`, invoked via `main.async` at `TranscriptionController.swift:1015-1039`
**Symptom:** Pasteboard path sleeps 20ms + schedules restore at +0.8s (dead code — see N1); keystroke path sleeps 20ms between down/up. Each dictation blocks main 20–40ms minimum. Long transcripts post as a single CGEvent with no chunking — some apps truncate very large single events.
**Fix:** move sleeps off the commit critical path (post key-up from a background queue); chunk keystroke injection (e.g. 2k UTF-16 units per event pair) for multi-paragraph dictation.
**Last verified:** FIX. Sleeps predate v0.9.7; never moved.

### ⚡ O4 — Daemon log still world-readable in /tmp

**Location:** `Sources/WhisperFlow/AppDelegate.swift:758` (`/tmp/wf-daemon.log`, created without `0600`)
**Symptom:** FIX-P1 (v0.9.7, CHANGELOG 0.9.7) moved the *app* log to `~/Library/Logs/WhisperFlow/app.log` 0600 because logs contain transcript text — but the *daemon* log stayed at world-readable `/tmp/wf-daemon.log`. Same sensitive content, old permissions.

### 🟢 N6 — 11 AppIcon files unhandled by SwiftPM (the build warning)

**Location:** `Package.swift` executableTarget (no `resources:`/`exclude:` for `Sources/WhisperFlow/Resources/`) — flagged files: `AppIcon.icns` + 10 `AppIcon.iconset/*.png`
**Symptom:** Every `swift build` emits `warning: 'whisperflow': found 11 file(s) which are unhandled; explicitly declare them as resources or exclude from the target`. **Fix:** declare the intent in `Package.swift`:

(or `exclude: ["Info.plist", "Resources/AppIcon.iconset"]` if the iconset must stay out of the bundle resources and come only via `build.sh`).
**Why it matters:** a permanently-yellow build hides future regressions; one-line fix.
**Last verified:** FIX — surfaced by the full uncached `swift build -c release` output (2026-10-02); never addressed in history.

## Strategic Recommendations

1. **One daemon-liveness helper.** `isRunning` (PID), `isReachable` (socket), and `proc_pidpath` verification (identity) are three separate checks used inconsistently — B2 is the proof. Fold all three into `TranscriptionDaemon.status() -> .healthy | .stalePid | .unreachable` with a single 1s budget, and route launch/stop/transcribe decisions through it. (Last verified: FIX — never consolidated.)
2. **Table-driven injection.** `inject()` is growing `if`-branches per app class (native → AX, Electron → keystrokes, pasteboard → Cmd+V). Make it a cached per-app strategy (`frontmost bundleID → .ax | .keystrokes | .pasteboard`, probed once and memoized) instead of per-call disk checks. Absorbs O1/O2 and the next Chromium/odd-app special case. (Last verified: FIX — `49a6f2e` added the second branch; no table exists.)
3. **Main-thread blocking audit.** B1 (3s), O3 (20–40ms ×2), and `relaunchSelf.waitUntilExit` (`AppDelegate.swift:612`, fast but still main) share one rule: main never blocks. A 10-minute pass moving all three to background queues with optimistic UI updates closes the class. (Last verified: FIX — FIX-R2/FIX-B5 fixed two instances in v0.9.7; three remain.)
4. **Daemon reports bytes consumed.** R3 exists because the client guesses WAV layout. Have the daemon's partial response include `bytes_consumed`, and have the client advance its offset from that instead of `frames × 2`. Removes an entire class of slice bugs. (Last verified: FIX — protocol is client-guessed today.)

1. B2 (stale PID) — silent total loss of the default engine; one-function fix.
2. B4 (uncapped delete) — only data-loss bug; three-line fix mirroring siblings.

5. O4 (daemon log perms) — privacy parity with FIX-P1; one-line path change.
6. R1 (send timeout) + O1 (Electron cache/Chromium) — robustness of the two newest paths.
7. R3/R4/R5, O2/O3, N-series — opportunistic; R3 before re-enabling partials by default.

## Learnings

- This codebase fixes thoroughly *per incident* but leaves sibling call sites uncovered (B4 vs FIX-10; O4 vs FIX-P1; B2 vs FIX-R7; R1 vs FIX-13). Future fix passes should grep for the pattern, not just patch the reported site.
- Prior-session audit notes that paid off and should not be re-litigated: WAV-deinit ordering (FIX-15/16), partial in-flight guard (FIX-R5b), daemon recv lock-confinement (FIX-R5), concurrent stderr drain (FIX-R1/R8), capture-queue serialization (FIX-R2), BT warm-up isolation (v0.9.7 R3 + v0.9.8.1 WarmUpGuard), Electron keystroke path (FIX-19, `748e05a`, `49a6f2e`) — all VERIFY, all holding.
- `isCapturing`/`iconGeneration`/serial-queue discipline is the load-bearing correctness pattern here; R2 is only benign because FIX-R2's guard exists. Treat those guards as invariants in future diffs.
- No test target exists; every finding above was verified by reading only. A Swift Testing target covering `MicEnergyTracker`, `FillerWordCleaner`/`GrammarCorrector`, and the HotkeyManager state transitions would be the cheapest regression net.
